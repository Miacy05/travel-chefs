vibe-coding-deploy第七节 · jsdom 跑完整流程
依据
不要靠「看起来没报错」交付；静态站也能在 Node 里跑端到端冒烟测试。 JSDOM 必须给 url:'http://localhost/'，断言要走真实 btn.click()。

把单文件 HTML 注入 jsdom，用 VirtualConsole 把 jsdomError 当成失败项； 断言一律走真实点击与真实等待（await sleep(700) 等关卡切换），覆盖进入 → 解锁 → 开始 → 通关 → 结算 → 存档。
复核

vibe-coding-deploy第十节 · Windows / PowerShell 踩坑清单
依据
先找 PortableGit 不要假设 PATH 里有 git；中文 commit 乱码是 PowerShell 按 GBK 解码的显示假象； 链式 git 命令的回显不可信，每条关键操作后要用独立复查命令核验；提交信息用 -F msg.txt 不要用 -m 传中文。
落地
PortableGit 前置到 PATH；用 Node execFileSync(...,'utf8') 读 git log 再写文件确认， 没有去「修」根本没坏的编码；每次 push 后用 git rev-parse HEAD 与 git ls-remote origin 比对。
复核

vibe-coding-deploy第十二节 · github.com 被阻断时的替代通道
依据
PowerShell 的 Invoke-WebRequest 会走坏掉的代理环境变量，制造「全网不通」的假信号； Node 默认不读 HTTP_PROXY，是最干净的可达性探针。github.com:443 挂了 ≠ GitHub 挂了， 可改用 ssh.github.com:443。
落地
用 Node 分别探测 github.com / api.github.com / ssh.github.com:443 / api.vercel.com， 确认直连失败、SSH over 443 握手成功后，改用 SSH over 443 推送；另按本节提示关掉仓库级 http.schannelCheckRevoke 解决证书吊销检查报错。
复核
30+ 次提交全部成功推送到 github.com/Miacy05/travel-chefs。

四、SRL 三阶段（前测 → 执行监控 → 后测与反思）

本次作业按自我调节学习（Self-Regulated Learning）的三阶段推进。前测、后测用同一套四问， 方便老师直接对照成长曲线；反思报告按要求写满「目标达成度 → 关键证据 → 关键转折 → 迁移计划」四段。

4.1 阶段一 · 前思 / 前测（目标设定与计划）

Q1 我要做出什么？
一款能真的玩起来的像素风「环游世界 + 模拟经营」网页小游戏：接待顾客 → 按配方备料 → 下锅 → 装盘 → 上菜 → 赚金币升级 → 攒星星解锁下一个地区。 交付形态明确为三项：公网可访问的 xxx.vercel.app 网页、公开的 GitHub 仓库、一份 Skill 驱动的过程记录页。
Q2 我现在的起点是什么？
会写一点 HTML / CSS / JS，但从没独立把项目部署到公网，也没系统用过 git 协作流程； 对 AI 协作的预期是「AI 能写代码，但架构决策和验收标准必须我自己把关」。
Q3 我打算怎么做？
拆成四步：① 先出方案文档与线框图，逐条确认再写代码；② 先打通一个地区的完整链路；③ 复用量产其余 4 个地区；④ 部署上线并用自动化测试验收。 每一步都指定用哪个 Skill 兜底（设计看设计系统那节、测试看 jsdom 那节、上线看 Vercel CLI 那节、网络不通看替代通道那节）。
Q4 怎么算做成了？
事先定死五条可验收判据：手机上能打开、能完整玩通一关、commit ≥ 3 次、单元测试全绿、三项交付物链接都能打开。

4.2 阶段二 · 表现 / 执行监控（过程记录）

决策点

单文件 vs 多文件：需求要求「每个模块都要能单测」，但静态托管又要求极简。
解法是先问再做，最终选「单个 index.html 内联全部代码，模块挂 window.TC 命名空间， 再在 tests/ 里按模块拆测试文件」——既保住零依赖部署，又拿到分模块覆盖。

自检动作

每个阶段结束跑一遍全量单测；关键操作后一律用独立复查命令核对，不信任链式命令的回显； 上线后回读线上字节并与本地做 sha256 对比，确认「线上就是最新版」而不是「本地改完了」。

卡点 + 解法

遇到卡点先定位再动手：例如 github.com:443 直连失败时，先做网络可达性探针确认是通道问题而不是账号问题， 再换 ssh.github.com:443 一次推成功；渲染越界时不去「盲改坐标」，而是写脚本穷举探测把越界项打印出来。

4.3 阶段三 · 后测（与前测同构，便于对照）

Q1 我做出了什么？
v2.5.0：5 个地区共 25 关，每个地区一套独立店铺场景与专属装修件； 顾客从右侧滑入到店、排队呼吸浮动、落座弹跳，耐心耗尽会冒 😠 离开；员工线收敛为单一「服务员」（Lv1 每 5 秒自动上菜 / Lv2 手动小费 +10% / Lv3 每 5 人全体耐心 +10%）。 线上 travel-chefs.vercel.app 与本地 index.html 逐字节一致。
Q2 起点回顾？
入学前完全没部署过。现在能用 vercel login --non-interactive 设备码登录、 vercel deploy --prod --yes 发布，并用 git ls-remote 独立核对远端 ref； 也知道了「项目名 = 域名前缀，仓库名要一起定死」。
Q3 实际怎么做的？
基本按前测的四步走完，但比计划多了一轮「地区差异化」迭代（店铺模型 / 装修 / 排队 / 员工简化）。 每轮结束都跑 23 个测试文件、用脚本穷举探测绘制边界，最后跑交付物自检脚本收尾。
Q4 达成判据？
五条全部达成：手机可打开 ✅ · 能玩通一关 ✅ · 30+ 次提交 ≥ 3 ✅ · 507 条断言全绿 ✅ · 三项链接均 HTTP 200 ✅。 自检脚本给出 100 / 100。
认知上变了什么

部署不是最后一步，从「建库命名」那刻就开始了 —— 仓库名和项目名决定了域名，后期改要付链接失效的代价。 另外「看起来没报错」不等于对，必须换成可度量的验收（断言数、边界探测、字节比对）。

能力上多了什么

会用 CLI 完成发布并回读校验；会用 jsdom 给静态单文件做端到端冒烟； 会用脚本穷举做边界探测替代肉眼验收；会把踩过的坑沉淀成可复用的 Skill 步骤。

  • 仓库提交历史：github.com/Miacy05/travel-chefs —— 30+ 次提交，作者统一为 Miacy05；最近两次分别落在「游戏本体」与「测试适配」，可看出改动是分层的。
  • 线上作品：travel-chefs.vercel.app —— 与仓库里的 index.html 逐字节一致（458668 字节 / sha256 680de66f…， 本页加载时实时回读计算，不写死）。

三、关键转折

转折 1：把「推送失败」重定义为「通道不通」。 最初 git push 失败，直觉判断是账号或权限问题，差点去重置凭据。 改用 Node 做可达性探针后才发现本机 github.com:443 直连被阻断，而 ssh.github.com:443 握手正常 —— 换成 SSH over 443 后一次推送成功。如果不是先做探针而直接改账号，这个问题会无解地卡住。

转折 2：把「看着不对」换成「量出来不对」。 5 个地区场景做出来后视觉上没发现异常，但穷举探测「5 地区 × 6 装饰等级 × 3 画布尺寸」时， 打印出巴黎遮阳棚和披萨砖墙会画到 x=161（画布只有 160 宽）。 这说明肉眼看不出 ≠ 没问题；补上夹取助手后所有尺寸都在界内，并新增了「地区绘制指纹唯一性」断言防止回归。

四、迁移计划

  • 把命名当成架构决策：仓库名、Vercel 项目名、域名前缀在建库那一刻就统一写死，避免后期改名导致所有已提交的链接失效。
  • 关键操作一律独立复查：push 后查 git ls-remote、部署后回读线上字节比 sha256， 永不把链式命令自己的回显当作成功依据。
  • 渲染类改动配可度量验收：凡是「画出来」的东西，都补一个能打印数字的探测脚本（边界 / 颜色 / 尺寸）， 不依赖肉眼；这次的做法已经可以直接复用到下一个项目。
  • 流程固化成 Skill：把「对照评分标准自检 → 生成 skill 证据表 → 产出记录页」这套收尾动作沉淀成 vibecoding-srl-trainer， 下次同类作业可以直接复用，不用重新摸索。

五、项目与需求

作品是一款像素风「环游世界 + 模拟经营」网页小游戏 Travel Chefs。 最初是基于配方点选的模拟经营原型（v1），升级为关卡制 + 地区解锁 + Canvas 像素场景 + 圆角卡片 UI 的正式版本（v2）。

用户确立的约束

  • 先出方案、确认后再写代码；
  • 每次改完必须跑全部单测；
  • 不自行添加没要求的系统；
  • 单 index.html 内联全部代码，模块挂 window.TC；
  • 5 个地区全部做可玩内容（25 关 / 15 道菜），不做占位；
  • 完全离线自包含（音效用 WebAudio 合成，不引任何图片 / 音频资源）。

八、踩过的坑（多为 Skill 提醒过、或补进 Skill 的经验）

  • git push 假回显：报「Everything up-to-date / nothing to commit」不代表没推成功，用 git ls-remote 比对远端 ref 才准。
  • PowerShell / Bash 工具不回显 stdout：结果一律写文件再读；git 输出按 GBK 解码会显示中文乱码（显示假象，非真写坏）。
  • github.com:443 时通时断：SSH over 443（ssh.github.com:443）是最稳的推送通道。
  • 代理环境变量制造假信号：Node 默认不读 HTTP_PROXY，用它做网络探针才准。
  • 测试驱动抓出 3 个真实 bug：出锅高亮用错变量（NaN 高度）、布局留白穿帮、底部导航切 tab 被路由吞掉。
  • 看不了图时的替代验收：用「溢出度量 + 画布颜色直方图 + 驱动游戏状态断言」代替肉眼截图； 用 CDP 的 Runtime.evaluate 把页面状态「读」回来做断言。
  • 肉眼看不出 ≠ 没问题：5 个地区场景视觉上都没异常，直到穷举探测「5 地区 × 6 装饰等级 × 3 画布尺寸」， 才打印出巴黎遮阳棚 / 披萨砖墙画到了 x=161（逻辑画布只有 160 宽）。
  • 测试夹具没归零会被误判成功能坏了：教程用例里 UI.TUT_DWELL 没置 0， 两次点击间隔不够，结果被读成「教程不推进」—— 其实是测试写法的问题。
  • 「断言过时」会伪装成「代码坏了」：教程从「按动作标签推进」重构为「按游戏状态推进」后， 旧断言必然失败。正确做法是先取一份基线（git show HEAD:）跑同一套测试， 确认哪些失败是这次重构的预期结果，再改测试；不要一看到红就去改实现。
  • 本地预览服务会自己挂掉：端口 ECONNREFUSED 时不要以为代码坏了， 用同一个只读脚本重启，再从磁盘和 HTTP 双向回读字节数确认服务恢复。
